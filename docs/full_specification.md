# A Formal Definition of an Input Projection

## Canonical Definition

An **Input Projection** is a finite, declarative specification of a constrained interaction between an agent and a system, whose sole purpose is to incrementally produce a locally valid data value.

This definition is intentional and minimal. Every term is essential.

---

## The Distinction: Input Projection vs. Form

The term *Form* is overloaded in common usage and conflates specification, user interface, persistence, and business logic. To eliminate this ambiguity, we draw a strict distinction.

* **Input Projection (The Ice)** The static, immutable specification. It defines the geometry of a valid input space. It is declarative, finite, and closed. It is a map.  
    
* **Form (The Water)** The ephemeral runtime artifact generated by an Engine interpreting an Input Projection. It is the transient interaction surface presented to an agent. It has no independent meaning outside the Projection that produced it. It is the journey through the map.

An Input Projection may generate many Forms across different runtimes, interfaces, or agents. The Form is an instance; the Input Projection is the truth.

---

## Clarification of Terms

### Input Projection

An Input Projection describes a specific projection of a data shape, optimized for capture.

It has the following properties:

* **Finite** It defines a bounded interaction space. It cannot express unbounded loops, recursion, or open-ended computation.  
    
* **Declarative** It specifies constraints on outcomes, not procedures. It contains no execution order, imperative logic, or side effects.  
    
* **Closed** It contains everything required to determine local structural validity. No external knowledge is required to understand or validate it.

An Input Projection is a specification, not an experience.

---

### Agent

An agent is any actor capable of supplying input in response to feedback.

An agent may be:

* a human  
* an automated script  
* a bot  
* a synthetic or adaptive system

The definition does not privilege human interaction or graphical interfaces.

---

### Locally Valid Data Value

The output of an Input Projection is a single data value that satisfies all declared constraints without reference to external state.

* **Included:** Types, formats, patterns, cardinality, internal consistency, structural invariants.  
    
* **Excluded:** Persistence concerns, database uniqueness, referential integrity, authorization, workflow state, business rules dependent on history or other records.

Local validity is evaluated purely from the produced value itself.

---

## Axioms of Input Projections

### Axiom 1\. Finite Interaction

Every Input Projection defines a finite interaction space.

Any specification that admits unbounded loops, recursion, or non-terminating behavior is not an Input Projection.

---

### Axiom 2\. Declarativity

An Input Projection specifies constraints on outcomes, not procedures.

It does not contain execution logic, event handlers, control flow, or side effects.

If understanding a specification requires imagining how it runs, it is not an Input Projection.

---

### Axiom 3\. Local Validity

An Input Projection enforces only those constraints that can be evaluated from the produced value itself.

If validity depends on external system state, time, history, or the existence of other values, that rule lies outside the Projection.

---

### Axiom 4\. Single Output

An Input Projection produces exactly one data value.

It does not persist data. It does not trigger actions. It does not modify the system.

It is a read-only map that yields a write-only value.

---

## The Litmus Test

A specification is a valid **Input Projection** if and only if:

1. It can be fully validated without external context (static analysis).  
2. It can be reasoned about without execution (no hidden state).  
3. It produces exactly one structurally valid data value.

If a specification requires a submit handler, an API call, or knowledge of application flow to be understood, it is not an Input Projection; it is an Application concern.

---

## Final Restatement

**An Input Projection is a finite, declarative specification that defines how an agent may construct a locally valid data value.**

A Form is merely the transient shadow cast when an Engine renders that specification into an interaction.


# The Primitive Set of an Input Projection

## Purpose

This document defines the **minimal and complete set of structural primitives** required to express every possible **Input Projection** while satisfying the axioms of **Finiteness**, **Declarativity**, and **Local Validity**.

Any specification that cannot be expressed using only these primitives is not an Input Projection; it is behavior.

---

## Foundational Claim

An Input Projection is a description of **data**, not computation.

Therefore, the Projection’s expressive power must be limited to the expressive power of **Algebraic Data Types (ADT)**.

If a structure cannot be expressed as a composition of these primitives, it is not data. It is code.

---

## The Minimal Complete Set

An Input Projection may be composed of exactly **five** structural primitives.

No additional structural primitives are permitted.

---

## 1\. The Scalar (The Atom)

### Definition

A **Scalar** is an indivisible value with no internal structure.

It is a leaf node in the Projection tree.

### Role

* Captures a single atomic value.  
* Serves as the termination point for traversal.

### Variations

* `String`  
* `Number`  
* `Boolean`  
* `Null`

### Adherence to Axioms

* **Finite:** A scalar has no internal expansion.  
* **Declarative:** It declares a value, not a process.  
* **Locally Valid:** Validity is determined entirely by its own value and constraints.

---

## 2\. The Struct (The Product Type)

### Definition

A **Struct** is a fixed collection of named Projections that must all be present together.

It represents logical **conjunction**.

### Role

* Groups multiple Projections into a single composite value.
* Defines internal structure without introducing behavior.

### Relations

A Struct may declare an optional `relations` array of cross-field predicates (see The Constraint Layer).

### Logic

A value of a Struct is valid if and only if **all** of its fields are valid **AND** all declared Relations evaluate to True.

Example logic:

A `Person` is a `Name` **AND** an `Age`.

### Adherence to Axioms

* **Finite:** The number of fields is fixed.
* **Declarative:** It describes shape, not construction.
* **Locally Valid:** Validity depends only on contained fields.

---

## 3\. The Union (The Sum Type)

### Definition

A **Union** defines a value that may take **exactly one** of a finite set of distinct shapes.

It represents logical **disjunction**.

A Union may optionally declare a **Default Variant**. If the discriminator is missing, the Default Variant is automatically active. This prevents the Union from starting in an `Incomplete` state.

### Role

* Expresses conditional structure without procedural logic.  
* Replaces `if/else`, visibility rules, and step logic.

### Constraint

All Unions **must be discriminated** by an explicit scalar value.

The active branch must be statically determinable.

### Logic

A value of a Union is valid if it conforms to **one and only one** branch.

Example logic:

A `Payment` is a `CardPayment` **OR** a `BankTransfer`.

### Adherence to Axioms

* **Finite:** The number of branches is fixed.  
* **Declarative:** Selection is structural, not procedural.  
* **Locally Valid:** Validation is confined to the chosen branch.

---

## 4\. The List (The Finite Sequence)

### Definition

A **List** represents a finite sequence of values, all conforming to the same Projection.

### Role

* Expresses cardinality and repetition.  
* Models collections without introducing iteration logic.

### Constraints

A List **must** declare an upper bound (`maxItems`).

Unbounded sequences are explicitly forbidden.

### Logic

A List is valid if:

* Its length is within declared bounds.  
* Every element is individually valid.

### Adherence to Axioms

* **Finite:** Cardinality is explicitly bounded.  
* **Declarative:** It describes allowed quantity, not generation.  
* **Locally Valid:** Validation depends only on contained values.

---

## 5\. The Reference (The Opaque Atom)

### Definition

A **Reference** is an atomic value whose internal meaning lies outside the Input Projection.

It represents a boundary crossing.

### Role

* Allows the Projection to point to external system concepts.  
* Preserves locality by validating format, not existence.

### Constraints

* Only the **key format** may be validated.  
* No lookup, resolution, or external verification is permitted.

### Logic

A Reference is valid if and only if it satisfies its declared format constraints.

### Adherence to Axioms

* **Finite:** It is atomic within the Projection.  
* **Declarative:** It describes a boundary, not a relationship.  
* **Locally Valid:** No external state is consulted.

---

## The Constraint Layer

Constraints are **not** structural primitives.

They are **predicates** applied to existing primitives to define the boundary of validity.

**Properties of Constraints** All constraint predicates must be:

1. **Pure:** Evaluation depends *only* on the input value and the declared constraint parameters. No side effects, no system time, no random numbers.
2. **Total:** The predicate must return a boolean result for *any* possible input value (including `null` or wrong types) without throwing an exception.

### Scalar Constraints

Scalars support type-specific constraints: `pattern`, `minLength`, `maxLength`, `enum` (strings); `min`, `max`, `multipleOf` (numbers); `enum` (booleans).

### Struct Constraints (Relations)

Structs support cross-field validation via an optional `relations` array. Each **Relation** is a declarative predicate comparing two sibling fields.

* **Locality:** Relations operate only between fields of the same Struct (sibling fields). Cross-struct or nested field references are forbidden.
* **Relation Object:**
    * `op`: The comparison operator. One of: `eq`, `neq`, `gt`, `lt`, `gte`, `lte`.
    * `left`: Field name of the first operand.
    * `right`: Field name of the second operand.
    * `label`: User-facing error message when the relation fails.

* **Allowed Operators:**
    | Operator | Meaning                  |
    |----------|--------------------------|
    | `eq`     | left == right            |
    | `neq`    | left != right            |
    | `gt`     | left > right             |
    | `lt`     | left < right             |
    | `gte`    | left >= right            |
    | `lte`    | left <= right            |

* **Evaluation:** Relations are evaluated only when both operand fields are present and individually valid. A missing or invalid operand does not cause the relation to fail—it is skipped.
* **Failure Reporting (Normative):** When a relation evaluates to False, the Engine MUST emit an Issue with:
    * `code: "relation_failed"`
    * `message` equal to the Relation’s `label`
    * `projectionPath` / `valuePath` pointing at the Struct node that declared the relation
    * `relatedProjectionPaths`: A list containing the absolute (root-relative) paths to the `left` and `right` operand nodes (deduplicated if `left === right`).
    * `relatedValuePaths`: A list containing the absolute (root-relative) paths to the `left` and `right` operand values (deduplicated if `left === right`).

### Other Constraints

* Struct: required fields
* Union: discriminator validity
* List: minItems, maxItems, uniqueness
* Reference: key format

Constraints refine structure; they do not add expressive power.

---

## Formal Grammar

An Input Projection may be defined recursively as:

Projection \=

  Scalar

| Struct(Projection\*)

| Union(Projection\*)

| List(Projection)

| Reference

All recursion must be finite and fully bounded.  
The graph of Projections must be a Directed Acyclic Graph (DAG).  
---

## Rejection Rule

Any proposed feature that cannot be expressed as a composition of these five primitives is not structural.

It introduces behavior.

Such features must be rejected at the Projection level.

---

## Summary

The five primitives define the **entire universe** of valid Input Projections.

They are:

* minimal,  
* complete,  
* closed,  
* and mathematically grounded.

This set forms the structural foundation upon which all Input Projections are built.

Anything beyond it is not data. It is code.  


# **Input Projection Abstract Machine**

## **Purpose**

Define the abstract machine (execution model) that interprets an **Input Projection** and governs incremental production of a **locally valid data value**, independent of UI, transport, persistence, and domain meaning.

## **1\. Core Objects**

### **1.1 Input Projection (P)**

A finite directed acyclic graph (DAG) of nodes drawn from exactly five primitives:

* Scalar  
* Struct (Product)  
* Union (Discriminated Sum)  
* List (Finite Sequence)  
* Reference (Opaque Atom)

### **1.2 Agent Stream (A)**

An agent produces a sequence of actions. The stream may be unbounded; finiteness is guaranteed by the Projection’s structure and bounds.

### **1.3 Value (V)**

A **Value** is an immutable snapshot of the payload at a given interaction step.

* At each transition, the machine produces a new Value Vₜ₊₁ derived from Vₜ.  
* Values are never mutated in place.  
* State at time T is distinct from state at time T+1.

This immutability requirement is fundamental to preserving declarativity and preventing hidden state.

At all times, a Value is interpreted relative to the Projection P.

## **2\. Machine State**

At discrete step t, the machine state is:

Sₜ \= ⟨ P, Vₜ, Cₜ, Σₜ ⟩

* **P**: the Projection (static)  
* **Vₜ**: the partial value at time t  
* **Cₜ**: the Cursor at time t  
* **Σₜ**: derived judgments at time t (validity, obligations, errors)

### **2.1 Cursor (C)**

Cₜ \= ⟨ π, ν ⟩

* **π**: address (path) to a node in the Projection  
* **ν**: address (path) to the corresponding location in the Value

The Cursor identifies the semantic location of interaction.

### **2.2 Node Judgment Lattice**

Each node is assigned exactly one judgment from a **four-state lattice**:

1. **Inactive**: the node is not applicable in the current Projection context (for example, a Union branch that is not selected). Inactive nodes contribute **nothing** to ancestor validity.  
2. **Invalid**: the node has **malformed** data or violates a constraint in a way that cannot be resolved by merely providing missing required descendants.  
3. **Incomplete**: the node is structurally well-formed so far, but is missing required information somewhere in its active subtree.  
4. **Valid**: the node is complete and satisfies all constraints in its active subtree.

This lattice is evaluated over the **active projection** induced by Union selections. Inactive nodes are pruned from evaluation.

## **3\. Node Semantics (Local Validity and Completion)**

Each primitive defines:

1. a shape function (permitted value forms)  
2. a judgment function (Inactive / Invalid / Incomplete / Valid)

### **3.1 Scalar**

* Shape: atomic value or missing  
* **Valid**: value present and satisfies scalar constraints  
* **Incomplete**: value missing while required (or otherwise required by a declared constraint), and no malformed data is present  
* **Invalid**: value present but violates a scalar constraint (wrong format, out of range, pattern mismatch, not-in-enum)  
* **Inactive**: not used for Scalars except when the Scalar resides in an Inactive subtree (for example, an unselected Union branch)

Requiredness does **not** make a node Invalid by itself. Missing required data is Incomplete; malformed provided data is Invalid.

### **3.2 Reference**

Same judgment rules as Scalar, except constraints are **format-only**. Existence is never validated.

### **3.3 Struct (Product)**

* Shape: object with named fields

Judgment is computed by aggregation over children plus local constraints (including relations):

* **Invalid**: any active child is Invalid, or any local constraint fails, or any relation fails (when both operands are present and valid)
* **Incomplete**: no active child is Invalid, and at least one required child is Incomplete or missing
* **Valid**: all required children are Valid, all present optional children are Valid, local constraints hold, and all relations evaluate to True
* **Inactive**: only when the Struct itself resides in an Inactive subtree

**Note on Relations:** Relations are only evaluated when both operand fields are present and individually valid. A relation with a missing or invalid operand is skipped (does not contribute to Invalid judgment).

### **3.4 Union (Discriminated Sum)**

A Union induces an **active subtree** by selecting exactly one variant.

**Stage 1: Selection**

* **Invalid**: discriminator value is present but malformed (fails its scalar constraints), or selects a non-existent variant key  
* **Incomplete**: discriminator missing and no default exists  
* Otherwise: select exactly one variant (using discriminator or default)

**Stage 2: Branch Evaluation**

* All non-selected variant subtrees are **Inactive**.  
* The selected variant subtree is evaluated normally.

Union judgment after selection:

* **Valid** iff selected variant is Valid  
* **Incomplete** iff selected variant is Incomplete  
* **Invalid** iff selected variant is Invalid  
* **Inactive** only when the Union itself resides in an Inactive subtree

### **3.5 List (Finite Sequence)**

* Shape: finite sequence

Judgment is computed by aggregation over items plus list constraints:

* **Invalid**: any item is Invalid, or list constraints fail, or length exceeds maxItems  
* **Incomplete**: no item is Invalid, and either length is below minItems or at least one item is Incomplete  
* **Valid**: length within \[minItems, maxItems\], every item Valid, and list constraints hold  
* **Inactive**: only when the List itself resides in an Inactive subtree

## **3.X Aggregation Rule (Normative)**

For composite nodes (Struct, Union, List), the machine uses the following aggregation rule over the **active** children:

1. If any active child is **Invalid**, the parent is **Invalid**.  
2. Else if any required active child is missing or **Incomplete**, the parent is **Incomplete**.  
3. Else the parent is **Valid**.  
4. Children in **Inactive** state are ignored entirely (they do not contribute to the parent’s judgment).

## **4\. Actions**

The agent interacts via a closed action alphabet.

Minimum action set:

1. **SetScalar(ν, x)**: set scalar/reference value at value-path ν  
2. **Unset(ν)**: remove value at ν  
3. **SelectVariant(ν, k)**: select union variant k (may be represented by setting the discriminator)  
4. **ListAdd(ν)**: add a new item to list at ν (subject to maxItems)  
5. **ListRemove(ν, i)**: remove item i from list at ν (subject to minItems)  
6. **MoveCursor(π, ν)**: request cursor movement; engine normalizes if needed

## **5\. Transition Function**

The engine is deterministic:

δ(Sₜ, aₜ) → Sₜ₊₁

Transition steps:

1. Apply action to produce candidate value V′ (if permitted)  
2. Normalize V′ by Projection structure:  
   * Remove values that no longer exist due to Union selection changes  
   * Reject illegal list cardinality operations  
3. Recompute judgments Σ′ (incrementally or globally)  
4. Update cursor C′ by cursor policy

Determinism: same Projection and same action sequence yields same state sequence.

## 

## **6\. Traversal and Cursor Policy**

Traversal defines a canonical enumeration used for navigation and obligation selection.

### **6.1 Canonical Order**

* Struct fields enumerated in declared order  
* Union enumerates only selected variant  
* List items enumerated by ascending index  
* Traversal is **Depth-First, left-to-right**

### **6.2 Cursor Normalization**

If the cursor points to a node that no longer exists (union branch change, list removal), the engine moves it:

1. to nearest existing ancestor  
2. then to the first actionable descendant by canonical order

Cursor movement is total, deterministic, and never points into a dead branch.

### **6.3 Cursor Authority**

The Canonical Order is **normative** for sequential navigation (Next/Previous).

* **Agent Jumps:** Agents may request discontinuous focus changes via MoveCursor.  
* **Engine Enforcement:** The Engine is the final authority. It strictly enforces that the resulting cursor position points to an **existing, active** node.  
* **Rejection:** Requests to enter Inactive or non-existent branches are rejected or normalized to the nearest valid location.

## **7\. Completion**

The machine is complete when the root node judgment is **Valid**. The corresponding V is the locally valid output.

Completion does not imply persistence, submission, authorization, or external correctness.

## **8\. Soundness and Non-Goals**

### **8.1 Soundness**

If the engine declares root **Valid**, then V satisfies all Projection constraints.

### **8.2 Non-Goals**

The abstract machine does not:

* call external systems  
* validate existence of references  
* enforce cross-record invariants  
* execute user logic  
* define UI layout
