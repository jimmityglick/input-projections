# Festival editor decisions

- **Session formats.** Switching variants discards the outgoing branch’s fields. Returning to a workshop starts with empty workshop materials.
- **Lost save acknowledgement.** Keep the draft and read the saved version. Matching content confirms the submitted value. An unchanged base permits a retry. If verification is offline, the next check reads again. A different saved revision and value requires reconciliation.
- **Entity identity and names.** Choose the ID when adding an entity. Its first confirmed save makes the ID read-only in the editor. During a save or verification, the editor holds the submitted ID fixed. A rejected first save releases it for correction. Display names remain editable and assignments keep referring to the same ID.

## What we learned from the demos

**One projection can span many entities.** The festival editor produces one program value. Venues contain rooms, stages, and sessions. Speakers and tracks are shared across those branches. A session holds a speaker ID, so changing a speaker’s display name in the directory also updates the name offered by the assignment picker. The projection defines the shape of the interaction. The renderer decides how a person navigates it, from a table in the work queue to folding sections in the festival. [Festival projection](../tests/fixtures/festival.json) · [Festival renderer](../renderer/festival.ts)

**Put each rule where the facts are available.** A workshop with 44 kits in stock and 36 seats illustrates both layers. Reserving 45 kits violates a relationship between two fields in the form and produces immediate feedback. Reserving 35 satisfies the stock constraint, but leaves a seat uncovered. The Go service rejects that save and keeps the previous program intact. It also checks relationships across branches, such as a speaker booked for overlapping sessions in different rooms. [Program rules and tests](../backend/festival_test.go)

**Compare values to decide whether there is anything to save.** Counting edit events made the form say “Unsaved changes” after someone typed the original name back. Comparing the current valid draft with the last acknowledged payload fixed both the label and the unnecessary auto-save. At submission time, capture the value actually sent. When its acknowledgement arrives, newer typing still belongs to the current draft. Manual save and auto-save can then share one write path. [Save controls](../renderer/save_controls.ts)

**A reference picker needs to reveal the choices.** During hands-on testing, a newly added track appeared in the same draft’s speaker qualifications. The relationship worked, but an empty “Track ID” text box gave the user little indication of what to enter. The current control offers autocomplete from the draft catalog. A candidate improvement is a visible chooser that displays track names and stores their IDs. A useful acceptance test is whether someone can assign a newly created track without looking up its ID. [Current reference controls](../renderer/festival.ts)

**Test round trips and edit order.** Reloading a valid row caught a different bug from switching a variant: loading a saved record should preserve its payload regardless of what record was open before. In Chromium, the tests also hold real save responses in flight while the user keeps editing, and apply four linked edits in all 24 orders. Compare the resulting server document and revision with the expected outcome. A green status message alone can miss an extra write or a lost edit.
